# 原始 MP4 详情大小诊断

观察日期：2026-09-30。本文记录现场证据；现行处理规则以[一期可靠保存规格](../specs/phase1-saving.md)为准。

## 现象与取证

最近一次 `archive saved` 发现 118 项，归档结清 78 项，另有 40 项原始 MP4 因“媒体响应长度与详情元数据冲突”保存失败、移除状态为 `none`。随后仅通过既有 Chrome Extension 能力读取用户指定的四个失败 Post 详情与媒体，不更新生产数据库、不发 DELETE；文件保存在临时目录。本文不保存私人媒体、完整地址或凭据。

| Post ID 前缀 | 详情 sizeBytes | Content-Length 与实际接收字节数 | 完整解码 |
| --- | ---: | ---: | --- |
| `8b2bef83` | 1612866 | 1209632 | 通过 |
| `ccdf3866` | 2199590 | 1649674 | 通过 |
| `d237f461` | 1672726 | 1254526 | 通过 |
| `b71a1e62` | 1649814 | 1237343 | 通过 |

四个响应均为 HTTP 200、`video/mp4`，未报告 Content-Encoding，最终 URL 与所选 URL 相同。完整接收至 EOF 后，字节数与 Content-Length 相等；`ffmpeg -v error -xerror ... -f null -` 均退出 0。将响应回放给修复前的下载校验，四个均复现原错误。

实际文件编码为 `data:video/mp4;base64,` 加标准 Base64 正文后，字符串长度与详情大小完全相等，即 `4 × ceil(文件字节数 / 3) + 22`，四个样本误差均为零。[Base64 编码规则](https://www.rfc-editor.org/rfc/rfc4648.html#section-4)及[Data URL 格式](https://www.rfc-editor.org/rfc/rfc2397.html#section-2)解释了该关系。

## 结论及边界

最有力的解释是 Grok 某条写入路径把 Data URL 字符串长度记录到 `sizeBytes`；未取得服务端实现证据，不能确定具体写入路径。其余 36 项未下载验证；全部 40 项详情大小都满足该公式要求的模 4 特征，但这不足以逐项证明相同原因。

采用仅限原始 MP4 的精确元数据匹配规则，保留完整响应和文件核验；不全面忽略详情大小、不改换媒体来源、不降级、不新增 ffmpeg 运行依赖。合成回归覆盖三种 Base64 填充长度、代表性现场大小、保存及复用、拒绝其他冲突与不完整响应；测试不含私人媒体。

该现场取证发生在修复前，不是修复后的真实保存或删除验收。后续运行 `retry` 会保持原 archive 目标并可能移除远端 Post，须作为独立现场操作。

## 修复后的离线回放

将上述四份已捕获的完整媒体响应回放给修复后的 `downloadToTemp`，全部通过，返回真实字节数与捕获时 SHA-256 一致（4 个样本、12 个断言）。回放只写临时目录，随后清理；不发布到正式归档、不访问生产数据库、不连接 Grok。这证明修复覆盖已观察到的响应形状，不代替现场 archive／retry 验收。
